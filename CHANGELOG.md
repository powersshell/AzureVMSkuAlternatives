# Changelog

## 2026-08-17
- **fix:** **The results list was squeezed into a tiny scroll box on ordinary laptop screens.** The page was built as a fixed-viewport app shell — `html, body` were locked to the window height with scrolling disabled — so the document itself could never scroll and every result had to be read through a nested scroll pane. The escape hatch that restored normal scrolling was keyed on **width** (`max-width: 900px`), but the problem is **height**: a 1610 × 1003 laptop window is wide, so it kept the desktop app shell despite having no vertical room. Combined with the "Before you migrate" panel added earlier today (~250 px of chrome pinned *above* the results), fixed chrome consumed **~92% of the viewport and the results list got ~83 px** — enough for part of one card, with card #2 reachable only by scrolling inside that sliver. Two competing scroll panes made it worse: scrolling with the pointer over the left source panel did nothing to the results, which read as the page being broken. The page now scrolls normally at every viewport size, with the results header (price model, OS, vendor and generation filters) and the source panel **sticky** so they stay reachable as you scroll. The Browse all VMs table scrolls with the page too, and its column headers now pin to the viewport instead of to an inner box. No functional or data changes — layout only.
- **feature:** **Recommendations are now ranked by more than raw spec similarity.** Every alternative previously scored on one thing: how close its specs were to the target. When vCPU and memory matched exactly, every term saturated at 100 and the score collapsed — searching `Standard_D2_v3` in East US returned 189 candidates sharing only **18 distinct scores**, with **24 tied at exactly 100.00** and the tie broken *alphabetically*. That put a **burstable v2** at the top of the list for a general-purpose v3 source (`Standard_B2as_v2`, a completely different performance model built on CPU credits), returned a **v3 confidential-computing size for a v4 memory-optimized source** (`Standard_E8s_v4` → `Standard_DC8ds_v3` — older *and* a specialty size), and buried the obviously-correct `Standard_F4alds_v7` at **#8** for a `Standard_F4s_v2` source. A new **recommendation score** now blends technical fit (60%) with how current the size's generation is (25%) and how closely it matches the source's workload family (15%), and the sort has a real tie-breaker chain instead of falling back to alphabetical. Across ten representative sources the correct same-family answer now ranks **#1 in all ten**, and the D2_v3 tie group drops from 24 sizes to 4. Applies to the site, the API, the MCP server and the PowerShell script.
- **fix:** **Modernization is scored relative to each family, not against v7.** The obvious approach — "v7 is best, v6 next" — is wrong, because not every family *has* a v7: **L-series tops out at v4** and **B-series at v2**. On an absolute scale those families can never score well, so a cross-family v7 always wins: a storage-optimized `Standard_L8s_v2` was answered with a **memory-optimized** `Standard_E8ads_v7`, and a burstable `Standard_B2s` with a **compute-optimized** `Standard_F2alds_v7`. Neither is a sane replacement. Each size is now scored against the newest generation its own family actually ships **in the region you searched** — so a family whose latest generation hasn't landed in that region is judged on what's genuinely available there. `Standard_L8s_v2` now returns `Standard_L8as_v4` and `Standard_B2s` returns `Standard_B2als_v2`.
- **feature:** **Migration considerations are surfaced on every result.** Ranking a v7 first without saying what changes underneath would be bad advice — Microsoft's own guidance is explicit that v6/v7 is a *planned upgrade*, not a blind resize. Each recommendation now carries badges for the platform changes you have to plan for: **Gen 2 (UEFI) required**, **MANA network adapter** (v6+, may need updated drivers), **local NVMe temp disk**, **architecture change** (Arm64 sizes need application binaries rebuilt), and **older generation than your source**. A "Before you migrate" panel shows an effort estimate driven by your *source* generation — Very low from v5, Low from v4, Moderate from v2/v3 — alongside the Assess → Plan → Migrate → Validate journey links from Microsoft Learn.
- **feature:** **A "Why this ranking?" breakdown on every result.** Ranking that can't be explained can't be trusted or argued with, so each card can expand to show the four score components and any penalties applied — including the retirement and capacity-limitation penalties that were already in effect but previously invisible.
- **feature:** **Two new controls: priority mode and architecture filter.** *Balanced* (default) uses the blend above; *Lowest cost* shifts weight toward cheaper alternatives. The architecture filter (**Any / x64 only / Arm64 only**) is a filter rather than a ranking mode on purpose — measured across ten sources, ranking by architecture produced an **identical top 5 in all ten cases**, so it earned no toggle, while filtering demonstrably changes what you see. Both are available on the site, in the MCP server (`priority_mode`, `architecture_filter`) and in PowerShell (`-PriorityMode`, `-ArchitectureFilter`).
- **improvement:** The existing `similarityScore` is **unchanged** and still means exactly what it did — pure technical fit — and the minimum-similarity threshold still filters on it. The recommendation score is a separate, additive field, so anything reading the API today sees the same numbers.
- **fix:** The NVMe badge is now labelled **"Local NVMe"**. The underlying flag measures the local *temp disk*, which only `d`-suffixed sizes have — not the remote-disk NVMe interface that the v6/v7 migration guidance discusses. The old label implied the latter.
- **improvement:** Added `scripts/check_recommendation_quality.py` and a CI check asserting the ranking properties above against the **live** API: a source's own family must lead, a burstable size must never lead for a non-burstable source, the #1 result must never be an older generation, retired or capacity-limited, cost mode must actually reorder results, and the top 5 must contain at least 3 distinct scores (the tie-collapse guard). It re-implements size-name parsing independently rather than importing it from the API, so the guard can't pass just because the API is self-consistently wrong. Negative-tested against production before the fix: **8 of 8 assertions failed**, reproducing every bug above.

## 2026-08-12
- **fix:** **The site's core "Find alternatives" search returned HTTP 500 for every VM size.** Fixing the missing-catalog bug (below) meant large disk-throughput values are now stored as 64-bit integers — but Azure Table Storage hands those values *back* wrapped in a container object rather than as plain numbers, and the comparison code did arithmetic on them directly. Any search, on any size, in any region, failed instantly with an internal server error; Browse all VMs kept working, which made the breakage look narrower than it was. Values are now unwrapped as they leave storage, so every read path sees a plain number again.
- **improvement:** Added `scripts/check_api_smoke.py` and a CI check that calls **every public endpoint** and fails on any error response or empty result. The four existing guards all inspect the *contents* of one endpoint, so all four were green while the site's primary flow was returning 500 — none of them actually called it. This check runs every six hours (endpoint health depends on cached data rewritten on a timer, so it can break with no code change) and deliberately includes a very large VM size, which only succeeds when 64-bit values both save and read back correctly.
- **fix:** **324 VM sizes — 24% of the East US catalog — were missing from the site entirely.** Every size whose uncached disk throughput exceeds ~2.1 GB/s failed to save, because Azure Table Storage stores whole numbers as 32-bit integers by default and rejects anything larger. The failure was caught and logged as a warning, so each refresh reported success while silently dropping a quarter of the catalog. The sizes lost were the largest and newest ones — precisely the ones people search for — including the entire **D128 / D160 / D192 v6 and v7** flagship families (`Standard_D128s_v6`, `Standard_D192s_v7`, `Standard_D160als_v7`). They could not be found in Browse all VMs, could not be looked up by name, and could never be recommended as an alternative, so anyone migrating *to* current-generation hardware was shown only smaller options. Large values are now stored as 64-bit integers, and a size that fails to save is logged as an error and reported in the refresh response instead of vanishing quietly. Affects the site, every API endpoint, the MCP server and the PowerShell script.
- **improvement:** Added `scripts/check_catalog_coverage.py` and a daily CI check that compares the **live** catalog against Azure's own list of sizes offered in a region, so a silent coverage loss can't recur. It deliberately uses the Compute SKUs API rather than the retail price list as its source of truth: retail still carries meters for long-retired families like `Basic_A0` and `Standard_A10` that Azure no longer offers, which would overstate the catalog by hundreds of sizes and produce false failures. Covers East US and West Europe, and reports sizes served that Azure no longer lists as well as sizes missing.
- **fix:** **All 246 constrained-vCPU sizes reported the wrong number of vCPUs.** Sizes like `Standard_E16-4s_v5` and `Standard_HB368-48rs_v5` exist precisely to expose *fewer* usable cores than their parent while keeping the parent's memory, storage and network throughput — the standard way to cut per-core software licensing (SQL Server, Oracle) without losing performance. Azure publishes both `vCPUs` (the parent's physical core count) and `vCPUsAvailable` (the cores actually usable), and we read the first. `Standard_E16-4s_v5` was published as **16 vCPUs instead of 4**; `Standard_HB368-48rs_v5` as **368 instead of 48**. This made every constrained size look identical to its parent, which defeated the entire reason to pick one, overstated licensing cost by up to 8×, corrupted the cost-per-vCPU figure, and skewed similarity ranking (which matches on vCPU count) so constrained sizes were ranked against the wrong workloads. Verified against Azure's own data: `vCPUsAvailable` matches the count in the size name for **246 of 246** constrained sizes and is identical to `vCPUs` for all **1,110** unconstrained ones, so the change is strictly more correct and alters nothing else. Fixed in the site/API, the MCP server (via the API) and the PowerShell script.
- **fix:** The eight **HBv5** sizes (`Standard_HB368rs_v5` and its constrained variants) were labelled **Intel** with no CPU generation and no performance score. HBv5 runs a custom Azure-exclusive **AMD EPYC 9V64H** (Genoa / Zen 4, with HBM3 memory) that appeared in no CPU table, and its name carries no vendor letter, so it fell through to the Intel default. They now report AMD, the correct Genoa (Zen 4) generation, and a performance score — which also makes them appear correctly when filtering by AMD.
- **fix:** **12 confidential-computing AMD sizes were labelled Intel and given the wrong CPU entirely.** Sizes carrying a qualifier segment before their version — the `_cc` confidential-compute marker (`Standard_DC32as_cc_v5`, `Standard_EC64ads_cc_v5`) — failed to match the series pattern, so they fell back to matching on family letters alone (`DC`) and inherited that family's *first-generation* CPU: an Intel Xeon **E-2176G (Coffee Lake, 2018)**. In reality they run an **AMD EPYC 7763 (Milan / Zen 3)**. Both the vendor and the CPU generation and performance score were wrong, so these sizes were excluded from AMD filters, ranked against the wrong CPU performance, and compared against the wrong baseline. The same parsing gap also hit accelerator-suffixed sizes (`Standard_NC4as_T4_v3`, `Standard_NV6ads_A10_v5`, `Standard_ND96isr_H100_v5`). Qualifier and accelerator segments describe the attached device, not the host CPU, and are now ignored when resolving the series. Combined with the isolated-size fix, sizes with no resolvable CPU generation dropped from **76 to 46** in East US.
- **fix:** **26 more sizes** now resolve a CPU generation and performance score. "Isolated" sizes (`Standard_E8is_v5`, `Standard_E16iads_v5`, `Standard_M128ids_v2`, `Standard_EC8ias_v5`) are dedicated-host variants running the *same* silicon as their base series, but the `i` feature letter made them fail to match any known series, so they showed a blank CPU generation and no score — leaving them unrankable on CPU performance.
- **improvement:** Added `scripts/check_vcpu_consistency.py` and a daily CI check that validates the **live** published vCPU counts. It asserts every size reports a positive vCPU count and that every constrained size's published count matches the number in its own name — an independent source of truth, since the name is set by Azure, not derived from the capability we read. Deliberately does *not* assume the leading number in a size name is a core count: for 52 legacy sizes (`Standard_D11`, `Standard_GS5`) it's a series index, not a vCPU count, and asserting otherwise would produce false failures. Like the other guards it fails if a check inspects zero rows, so it can't silently become a no-op.
- **fix:** **107 AMD VM sizes in East US were labelled Intel.** CPU vendor was inferred from a single regex over the size name that only recognised one suffix shape (`…as_v5`, `…ads_v5`), so it missed every AMD size shaped differently: sizes with other feature letters between the `a` and the `s` (`Standard_F2ams_v6`, `Standard_F1amds_v7`, `Standard_B2ats_v2`, `Standard_L2aos_v4`), sizes with no `s` at all (`Standard_D2a_v4`, `Standard_E2a_v4` — despite the code comment claiming these were handled), sizes ending in an accelerator instead of `_v` (`Standard_NC4as_T4_v3`, `Standard_EC4ads_cc_v5`, `Standard_NV6ads_A10_v5`), and the AMD EPYC **HB/HX HPC families**, whose names carry no vendor letter at all (`Standard_HB120rs_v3`, `Standard_HX176rs`). The data openly contradicted itself: 93 of these sizes were shown as **Intel** while simultaneously reporting a CPU generation of **"Rome (Zen 2)"**, **"Milan (Zen 3)"** or **"Turin (Zen 5)"** — Zen is AMD-only. Because vendor is a **filter** on the site, in the MCP server (`cpu_vendor`) and in the PowerShell script (`-CpuVendor`), these sizes were also silently missing from "show me AMD" results and wrongly included in Intel ones. Vendor is now resolved from the curated CPU-generation mapping first (which is derived from the actual CPU model Azure documents, so it is right even for the HPC families) and falls back to Azure's documented name grammar, in which the additive-feature letter `a` means AMD and `p` means Arm. Fixed identically in the site/API, the MCP server (via the API) and the PowerShell script.
- **improvement:** Added `scripts/check_vendor_consistency.py` and a daily CI check that validates the **live** published CPU vendors against two independent sources of truth: the CPU generation the API itself publishes (no Intel part is "Zen", no AMD part is "Neoverse") and Azure's documented VM name grammar. It also fails if a check inspects zero rows, so a change to the API response shape can't turn the guard into a silent no-op. Covers East US and West Europe on every API change and once a day, so a bad cache refresh is caught even when no code changed.
- **improvement:** Added `scripts/check_pricing_invariants.py` and a daily CI check that validates the **live** published prices against Azure's retail price list. Azure exposes several meters per VM size that share the same size name — pay-as-you-go, Spot, the deprecated Low Priority tier, Windows, and reservations — and picking the wrong one produces a plausible-looking number instead of an error, which is exactly why the Spot bug below survived unnoticed. The check asserts that Spot never exceeds pay-as-you-go, that every published Spot price traces to a genuine Spot meter (never a Low Priority one), that no Windows meter is reported as a Linux price, and that no reservation term-total leaks into an hourly field. It validates East US and West Europe on every API change and once a day, so a bad cache refresh is caught even when no code changed.
- **fix:** **Spot prices were wrong for hundreds of VM sizes.** The bulk pricing collector treated Azure's deprecated **"Low Priority"** meter — a Batch-only tier that is a different product with different prices — as if it were **Spot**. Where a size published both meters (962 sizes in East US), the collector kept whichever appeared first in the API response, so roughly half stored the Low Priority price as the Spot price. In East US this made the Spot price wrong for **472 sizes**, with **29 off by 10% or more** and a worst case of **99.8%**. `Standard_B2as_v2` showed **$0.015/hr** instead of the true Spot price of **$0.06768/hr** (4.5× understated), and `Standard_D64as_v5` showed **$0.55/hr** instead of **$0.580947/hr**. The bug only affected the cached path — which serves **USD**, the default — so the same size at the same moment reported Spot at **20% of pay-as-you-go in USD but 90% in EUR**. Low Priority meters are now discarded outright and only true Spot meters are used, matching the per-size lookup that was always correct. Affects the site, the `/api/grid`, `/api/skus` and `/api/compare_vms` endpoints, the MCP server, and recorded price history.
- **fix:** Reserved-instance meters are now classified **before** Spot. A reservation labelled as Spot would previously have had its **full 1- or 3-year term total** written into the hourly Spot field. No size hits this today, but the ordering was one upstream label change away from publishing a wildly wrong hourly price.
- **fix:** A **Windows** price can no longer be silently reported as a size's **Linux** price. When a size published no Linux meter, the collector fell back to the first meter it had — which could be Windows. It now reports no Linux price rather than a mislabelled one. Only `_Promo` sizes (already excluded from results) were affected in practice.
- **fix:** A **partially fetched** region can no longer corrupt the cache. The pricing collector paginates and gives up after 3 failed retries, returning whatever it had; the daily refresh then wrote that partial result straight to storage — blanking prices for every size on the unfetched pages and recording a **phantom price-change point** in history. Refreshes now refuse to persist an incomplete fetch and leave the previous good prices in place. This is the mechanism behind an observed missing Windows price for `Standard_D64as_v5` on 2026-08-11.

## 2026-08-11
- **fix:** Constrained-vCPU **Dsv2** sizes (`Standard_DS11-1_v2`, `DS12-2_v2`, `DS13-4_v2`, `DS14-8_v2` and friends) were **not** being flagged as retiring, because the retirement pattern didn't allow the `-N` suffix that constrained variants carry. Seven sizes in each region were shown as clean alternatives despite retiring with the rest of the Dsv2 series on 2028-05-01. They now carry the retirement badge, date and migration link like their parent series.
- **fix:** The `Standard_B<n>ls` retirement entry was dead code — an earlier, broader B-series pattern always matched first, so the entry could never take effect. Reordered so narrower patterns are evaluated first. No user-visible change today (both entries carried the same date), but the entry now actually works if `Bls` ever diverges.
- **improvement:** Documented the **VM SKU lifecycle runbook** (`docs/sku-lifecycle-runbook.md`), covering how a capacity-limited size transitions when it's later announced for retirement. Short version: **add the retirement entry and leave the growth-restriction entry in place** — the two signals are independent and both stay true. This is already the steady state for **102 sizes across 13 series**.
- **improvement:** Added `scripts/check_sku_lifecycle.py`, a reconciliation check for the hand-maintained retirement and capacity-limitation tables. It verifies the Python and PowerShell copies stay in lockstep, detects size-series where retirement flagging is inconsistent (which is how the Dsv2 gap was found), flags patterns permanently shadowed by an earlier one (which is how the `Bls` bug was found), reports the dual-flag overlap, and optionally checks that every Microsoft Learn link still resolves.
- **feature:** The **Site Usage Analytics workbook** gained a **Where Users Find Answers** section that shows how visitors navigate the site's two entry points — **Find Alternatives** (pick a size, get ranked replacements) and **Browse all VMs** (scan every size in a region). It's framed as coverage, not a competition: tiles cover **surface coverage** (how many people reach each area and how many use both), **daily unique users in each area**, **engagement depth** (avg/median actions per user per area), a full **what users actually do in each area** breakdown of every tracked action, the **Browse → Find Alternatives handoff**, **movement between areas**, and **where the answer landed** (exports and deep-dive actions attributed to the area they came from).
- **feature:** The workbook also gained a **Site → MCP funnel** tile showing how many visitors open the "Use with AI" instructions and how many copy a config, connecting site traffic to MCP server adoption.
- **improvement:** Every frontend telemetry event now records which area of the site the user was on when it fired, so shared features (price history, "where is this cheapest?", cross-region availability, exports) can be attributed to the area they were opened from. Area switches also record where the user came from. Still fully anonymous — no PII.
- **feature:** Added **growth-restricted (capacity-limited) VM size awareness** across the whole tool. Microsoft has published capacity limitations (effective **July 2026**) for a large set of previous-generation series — new subscriptions can't deploy them, and existing subscriptions won't be granted additional quota, even though most of these series are **not** retired and remain fully supported. The site now shows a **🔒 Limited** badge on affected alternatives and grid rows, a warning banner (with recommended migration targets and a link to the Microsoft doc) when the size you're comparing is affected, and a `🔒 Limited` suffix in the size picker. Affected sizes are **still shown by default** — they're valid, supported sizes — but they carry a ranking penalty so genuinely scalable alternatives sort higher, and a new opt-in **"Hide growth-restricted"** filter removes them entirely. Retirement and capacity limitation are tracked independently, so a size can be flagged as one, both, or neither.
- **feature:** The **MCP server** gained a `list_growth_restricted_skus` tool (full catalog, or a single size via `sku=`), and every SKU-returning tool now includes `growthRestricted`, `growthRestrictionSeries`, and `recommendedTargets` so AI agents stop recommending sizes a customer can't scale into. Backed by a new anonymous `/api/growth-restrictions` endpoint.
- **feature:** The **PowerShell script** reached parity: a `GrowthRestricted` column in the results table, a yellow warning for a capacity-limited target size (with recommended targets and the doc link), the same ranking penalty, and a new `-HideGrowthRestricted` switch.
- **data:** Added the capacity-limitation table covering **31 size patterns** across compute optimized (F, Fs, Fsv2), general purpose (D, Ds, Dv2, Dsv2, **Dv3, Dsv3, Dv4, Dsv4, Ddv4, Ddsv4, Dav4, Dasv4**, B/Bs, Av2/Amv2), memory optimized (**Ev3, Esv3, Ev4, Esv4, Edv4, Edsv4, Eav4, Easv4**, G, Gs), and storage optimized (Ls, Lsv2), each with its recommended migration targets. Source: [Previous-generation series capacity limitations](https://learn.microsoft.com/azure/virtual-machines/migration/sizes/previous-gen-series-capacity-limitations).

## 2026-07-20
